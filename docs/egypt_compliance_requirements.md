# متطلبات الامتثال الضريبي والفاتورة الإلكترونية المصرية
# Egyptian Tax Compliance & ETA E-Invoicing Architecture Requirements

> **إخلاء مسؤولية تنظيمي:** تم إعداد هذه الوثيقة لمساعدة المطورين وإدارة المنشأة على فهم متطلبات مصلحة الضرائب المصرية (ETA). كل بند موسوم بدرجة توثيقه القانوني:
> - `[رسمي مؤكد]`: مطابق للمواصفات الرسمية المنشورة على بوابة منظومة الفاتورة الإلكترونية وموقع SDK الرسمي لمصلحة الضرائب المصرية.
> - `[مصدر ثالث غير مؤكد]`: مستخرج من مصادر ثانوية أو مكتبات مفتوحة أو تجارب مطورين، ويخضع للتحقق والمراجعة المحاسبية.
> - `[غير موجود / غير مطبق حالياً]`: متطلب مستقبلي غير مفعل في مرحلة العمل الحالية.

---

## ماذا يعني هذا بالعملي (لصاحب العمل غير المحاسب)؟

> **خلاصة بسيطة:**  
> مصلحة الضرائب المصرية تطلب أن تصدر كل فاتورة للشركات بتنسيق رقمي موحد (JSON) عبر الإنترنت، وأن تُوقع بختم إلكتروني مشفر (USB Token) قبل إرسالها.  
> **حالياً:** شركتكم غير مسجلة في المنظومة ولا تمتلك التوكن. لذلك، صممنا النظام بحيث يعمل داخلياً بنسبة 100% دون توقف (إصدار فواتير، حساب الضريبة 14%، إدارة المخزن)، مع تجهيز بنية البيانات لتكون متوافقة تماماً مع الضرائب المصرية، بحيث إذا قررتم التسجيل وشراء التوكن مستقبلاً، يتم الربط بضغطة زر دون الحاجة لإعادة بناء النظام أو تعديل الفواتير القديمة.

## 1. أنواع المستندات في منظومة الفاتورة الإلكترونية (Document Types)

| الرمز | نوع المستند | الاستخدام | درجة التأكيد |
| :---: | :--- | :--- | :---: |
| `i` | **فاتورة مبيعات محلية (Invoice)** | الفاتورة العادية الموجهة لشركات أو جهات داخل مصر. | `[رسمي مؤكد]` |
| `c` | **إشعار دائن (Credit Note)** | يُصدر لتقليل قيمة فاتورة سابقة (مردودات مبيعات، خصم ممنوح بعد البيع). | `[رسمي مؤكد]` |
| `d` | **إشعار مدين (Debit Note)** | يُصدر لزيادة قيمة فاتورة سابقة (مصاريف إضافية، خطأ في السعر بالزيادة). | `[رسمي مؤكد]` |
| `ei` | **فاتورة تصدير (Export Invoice)** | فواتير البضائع أو الخدمات الموجهة لعميل خارج مصر (ضريبة 0%). | `[رسمي مؤكد]` |
| `ec` | **إشعار دائن تصدير (Export Credit Note)** | تسوية بالخفض على فاتورة تصدير سابقة. | `[رسمي مؤكد]` |
| `ed` | **إشعار مدين تصدير (Export Debit Note)** | تسوية بالزيادة على فاتورة تصدير سابقة. | `[رسمي مؤكد]` |
| `ii` | **فاتورة استيراد (Import Invoice)** | تسجيل البضائع المستوردة من الخارج عبر الجمارك. | `[رسمي مؤكد]` |

- **إصدار هيكل الوثيقة:** الإصدار الرسمي المعتمد حالياً هو `v1.0` للفاتورة الإلكترونية `[رسمي مؤكد]`.

## 2. أطراف المعاملة وتصنيف العملاء (Issuer & Receiver)

### أ. نوع المُصدِر (Issuer):
- نوع المنشأة: مسجلة كشركة `B` (Business) `[رسمي مؤكد]`.
- البيانات الإلزامية: الرقم الضريبي (9 أرقام)، الاسم التجاري، العنوان المنظم، كود النشاط الضريبي (Taxpayer Activity Code - 4 أرقام)، وكود الفرع المسجل لدى الضرائب (ETA Branch Code).

### ب. نوع المستلم (Receiver):
1. **شركة محلية `B` (Business):**
   - الرقم الضريبي التسجيلى (Registration Number) إلزامي (9 أرقام).
   - حظر قطعي: لا يجوز أن يتطابق الرقم الضريبي للمستلم مع المُصدِر `[رسمي مؤكد]`.
2. **فرد / مستهلك نهائي `P` (Person):**
   - الرقم القومي (National ID): إلزامي إذا تجاوزت قيمة الفاتورة حداً معيناً (حسب تعليمات المصلحة، عادة 50,000 جنيه مصري في الفاتورة B2B)، ومكون من 14 رقماً `[رسمي مؤكد]`.
   - للفواتير الأقل من الحد الأدنى، يُقبل بدون رقم قومي أو يُحول لمنظومة الإيصال الإلكتروني.
3. **أجنبي / عميل تصدير `F` (Foreigner):**
   - رقم جواز السفر أو المعرف القومي لبلده، مع تحديد رمز الدولة (كود ISO مثل AE, SA, US) `[رسمي مؤكد]`.

## 3. هيكل الفاتورة والحقول الحسابية (Invoice v1.0 Structure)

```json
{
  "issuer": {
    "type": "B",
    "id": "123456789",
    "name": "اسم شركتك بالعربية",
    "address": {
      "country": "EG",
      "governorate": "القاهرة",
      "regionCity": "المعادي",
      "street": "شارع النصر",
      "buildingNumber": "15"
    }
  },
  "receiver": {
    "type": "B",
    "id": "987654321",
    "name": "شركة العميل",
    "address": { "country": "EG", ... }
  },
  "documentType": "i",
  "documentTypeVersion": "1.0",
  "dateTimeIssued": "2026-11-04T12:00:00Z",
  "taxpayerActivityCode": "4690",
  "internalId": "INV-D1-000001",
  "invoiceLines": [ ... ],
  "totalSalesAmount": 1000.0000,
  "totalDiscountAmount": 0.0000,
  "netAmount": 1000.0000,
  "taxTotals": [
    { "taxType": "T1", "amount": 140.0000 }
  ],
  "extraDiscountAmount": 0.0000,
  "totalItemsDiscountAmount": 0.0000,
  "totalAmount": 1140.0000
}
```

### القواعد الحسابية الملزمة:
- `netAmount = totalSalesAmount - totalDiscountAmount` `[رسمي مؤكد]`.
- `totalAmount = netAmount + مجموع_الضرائب - extraDiscountAmount` `[رسمي مؤكد]`.
- في فواتير التصدير (`ei`): حقل `serviceDeliveryDate` إلزامي `[رسمي مؤكد]`.

## 4. بنود الفاتورة وتكويد الأصناف (Line Items & Coding)

### أ. أنظمة تكويد الأصناف:
1. **نظام GS1 الدولي:**
   - كود الصنف الدولي (GTIN) ويبدأ عادة بأرقام مثل 622 للمنتجات المصرية.
   - يتطلب اشتراكاً سنوياً مدفوعاً مع منظومة GS1.
2. **نظام EGS المحلي (المجاني لمصلحة الضرائب):**
   - تركيبة الكود: `EG-<الرقم الضريبي للشركة>-<كود الصنف الداخلي>`.
   - مثال: `EG-123456789-ITM001`.
   - يتطلب ربط كل صنف بكود تصنيف عالمي GPC (Global Product Classification) والموافقة عليه على بوابة الضرائب قبل استخدامه في الفواتير `[رسمي مؤكد]`.

### ب. وحدات القياس (Unit Types):
- رموز قياسية دولية (UN/ECE): مثل `KGM` (كيلوجرام)، `EA` أو `C62` (قطعة/عدد)، `LTR` (لتر)، `MTR` (متر) `[رسمي مؤكد]`.

## 5. جدول الضرائب وأنواعها الفرعية (Tax Types & Subtypes)

| رمز الضريبة | الاسم العربي | الأنواع الفرعية الشائعة | النسبة الافتراضية | حالة الشركة الحالية |
| :---: | :--- | :--- | :---: | :--- |
| **`T1`** | **ضريبة القيمة المضافة (VAT)** | `V009` (سلع عامة 14%)<br>`V001` (تصدير 0%)<br>`V006` (آلات ومعدات 5%)<br>`V007` (إعفاءات اتفاقيات) | 14% | **مفعلة أساسية** |
| **`T2`** | **ضريبة الجدول النسبية** | `Tbl01` (سلع جدول بنسبة مئوية) | متغير | **غير مخاطب بها (لا توجد سلع جدول)** |
| **`T3`** | **ضريبة الجدول النوعية القطعية** | `Tbl02` (قيمة قطعية بالجنيه) | مبلغ ثابت | **غير مخاطب بها** |
| **`T4`** | **الخصم تحت حساب الضريبة (Withholding)** | `W001` مقاولات (1%)<br>`W002` توريدات (1%)<br>`W003` مشتريات (1%)<br>`W004` خدمات (3%)<br>`W006` سمسرة وعمولات (5%)<br>`W010` أتعاب مهنية (5%) | 1% إلى 5% | **معطلة افتراضياً وتُفعل بقرار** |
| **`T5` - `T20`** | **رسوم إضافية وتنمية موارد** | رسم تنمية، تأمين صحي شامل، دمغة... | متنوع | **غير مفعلة حالياً** |

> **قاعدة حاسمة:** لا يجوز تكرار نفس كود `taxType` أكثر من مرة واحدة في نفس سطر البند `[رسمي مؤكد]`.

## 6. العملة وأسعار الصرف وتعارض الدقة العشرية (Currencies & Decimals)

1. **العملة الأساسية:** الجنيه المصري `EGP` كود ISO 4217 `[رسمي مؤكد]`.
2. **العملات الأجنبية (تصدير / بيع بالدولار أو اليورو):**
   - حقول إلزامية عند البيع بغير الجنيه:
     - `currencySold`: كود العملة (مثل `USD`, `EUR`).
     - `currencyExchangeRate`: سعر صرف البنك المركزي المصري المعلن في تاريخ الفاتورة `[رسمي مؤكد]`.
     - `amountEGP`: القيمة المقابلة بالجنيه المصري.
3. **تعارض الدقة العشرية (Decimal Precision Conflict):**
   - **في نظامنا (Cash ERP):** الحسابات وسعر الصرف يُخزن بـ **6 خانات عشرية** (`numeric(18,6)`) لمنع تآكل الفروقات المالية.
   - **في قواعد مصلحة الضرائب (ETA SDK / eReceipt):** الحد الأقصى المسموح به لسعر الصرف والمبالغ في بعض واجهات الإرسال هو **5 خانات عشرية** `[مصدر ثالث غير مؤكد]`.
   - **الحل الهندسي المقترح:** الحفاظ على 6 خانات داخلياً في دفتر الأستاذ العام لضمان الدقة المحاسبية، وتقريب سعر الصرف إلى 5 خانات فقط لحظة توليد ملف الـ JSON الموجه لمصلحة الضرائب.

## 7. دورة الإلغاء وتعديل الفواتير (Cancellation & Immutability)

1. **مهلة الإلغاء الرسمية:**
   - تتيح المصلحة إلغاء الفاتورة من خلال البوابة خلال مهلة زمنية محددة من تاريخ إصدارها (يحددها النظام المركزي لـ ETA، وغالباً ما تكون 72 ساعة في البيئة الإنتاجية) `[رسمي مؤكد]`.
   - **شرط عدم وجود مستندات مرتبطة:** لا يمكن إلغاء فاتورة إذا كان قد صُدر عليها إشعار دائن أو مدين نشط إلا بعد إلغاء الإشعار أولاً `[رسمي مؤكد]`.
2. **ما بعد انقضاء المهلة (التسوية عبر الإشعارات):**
   - إذا انقضت مهلة الإلغاء القانونية، **يستحيل إلغاء الفاتورة**.
   - الحل المحاسبي والضريبي الوحيد هو إصدار **إشعار دائن (Credit Note - `c`)** بكامل القيمة لإلغاء الأثر المالي والضريبي دون طمس الفاتورة الأصلية `[رسمي مؤكد]`.

## 8. مسار التوقيع الرقمي (Digital Signature Pipeline)

```
[فاتورة معتمدة محلياً]
         │
         ▼
[تحويل لصيغة Canonical JSON وفق معايير ETA]
         │
         ▼
[تجزئة التشفير SHA-256 للبيانات]
         │
         ▼
[وكيل التوقيع المحلي (Local Signing Agent) على جهاز الـ PC]
         │
         ├─► [USB Hardware Token - ePass2003]
         │       (شهادة التوقيع الرقمي CAdES-BES الصادرة من Egypt Trust أو مصر للمقاصة)
         │
         ▼
[إدراج التوقيع Base64 في مصفوفة signatures بالفاتورة]
         │
         ▼
[إرسال الحزمة الموقعة إلى بوابة مصلحة الضرائب]
```

> **ملاحظة تشغيلية:** بما أن أجهزة الكاشير أو الهواتف المحمولة لا يمكن توصيل فلاشة الـ USB Token بها مباشرة، فإن التصميم المعتمد يفصل بين مرحلة إصدار الفاتورة محلياً، ومرحلة التوقيع والإرسال التي تتولاها محطة مركزية على جهاز كمبيوتر مثبت عليه التوكن.

## 9. منظومة إيصال المستهلك الإلكتروني (B2C eReceipt v1.2)

- **الفرق الجوهري:** مخصص للمبيعات المباشرة للمستهلك الفردي النهائي (نقاط البيع POS).
- **الإصدار الحالي:** v1.2 `[رسمي مؤكد]`.
- **المتطلبات الإضافية:** تسجيل كل ماكينة كاشير بنقطة بيع افتراضية تمتلك معرف UUID فريداً ومفتاح تشفير خاصاً بها، وربط أرقام الإيصالات بتسلسل يومي لا يقبل التكرار على مستوى نقطة البيع.
- **الوضعية الحالية للمشروع:** مؤجل بالكامل إلى **المرحلة 8 (نقاط البيع POS)**.
