# وثيقة تصميم المرحلة 2c: حل النزاعات والمصادقة المحلية الآمنة
# Phase 2c Design: Conflict Resolution & Secure Offline Authentication

> **الحالة:** معتمد للتنفيذ  
> **النطاق:** (1) شاشة وخدمة حل النزاعات `/sync-conflicts`، (2) شارة النزاعات في واجهة المستخدم، (3) معمارية تسجيل الدخول أوفلاين مع قيود الصلاحيات وانتهاء الصلاحية والحظر الفوري عند العودة للاتصال.

---

## 1. شاشة وخدمة حل النزاعات (Conflict Resolution)

### 1.1 مصادر نشوء النزاع (Conflict Triggers)
ينشأ النزاع في نظام `cash` في حالتين أساسيتين:
1. **أثناء السحب (Pull Collision - `safeApplyServerRow`):**
   عند ورود سجل من السيرفر برقم تسلسلي أعلى (`server_seq > local.server_seq`)، بينما يوجد تعديل محلي معلق لنفس السجل في جدول `outbox` بحالة `pending` أو `in_flight` أو `failed`.
2. **أثناء الدفع (Push Concurrency - `sync_push_op`):**
   عند إرسال عملية تعديل محلية بنسخة قديمة (`base_version < server_version`)، فيرفض السيرفر العملية بحالة `status: 'conflict'` ورسالة `"Server version has changed"`.

في الحالتين، يتم حجز السجل في جدول Dexie `sync_conflicts` لمنع الكتابة فوق العمليات المعلقة وضمان عدم فقدان أي بيانات محلية دون موافقة المستخدم.

### 1.2 نموذج بيانات النزاع (`SyncConflict`)
```typescript
export interface SyncConflict {
  id: string; // UUID
  entity: string; // اسم الجدول (مثل items, documents, parties)
  entity_id: string; // معرف السجل
  local_payload: Record<string, any>; // البيانات المحلية المعلقة
  server_payload: Record<string, any>; // بيانات السيرفر الحالية
  base_version?: number | null; // النسخة التي بُني عليها التعديل المحلي
  resolved_at?: string | null; // تاريخ وتوقيت الحل
  resolved_by?: string | null; // المستخدم الذي قام بحل النزاع
  resolution?: 'keep_local' | 'keep_server' | 'merged' | null;
}
```

### 1.3 مسارات الحل البرمجية (Resolution Strategies)
تتيح شاشة النزاعات خيارين حاسمين للمستخدم:

1. **اعتماد بيانات السيرفر (Server Wins - `resolveServerWins`):**
   - استبدال السجل المحلي في Dexie ببيانات السيرفر (`server_payload`).
   - إزالة كافة العمليات المعلقة المتعلقة بهذا السجل من `db.outbox` حتى لا يُعاد إرسال التعديل المحلي الملغي.
   - وسم النزاع في `sync_conflicts` كـ `keep_server` مع تسجيل توقيت الحل `resolved_at`.

2. **إعادة تطبيق التعديل المحلي (Re-apply Local - `resolveLocalWins`):**
   - **قيد الحصانة الصارم (Immutability):** إذا كان المستند معتمداً (`status === 'posted'` في السيرفر أو محلياً)، يُحظر هذا الخيار نهائياً؛ لأن محفزات قاعدة البيانات `block_posted_changes` و `block_posted_children` سترفض التعديل حتماً. يُعرض تنبيه بالعربية: `"المستند معتمد نهائياً في السيرفر ولا يمكن تعديله"`.
   - **للسجلات القابلة للتعديل (مسودات، أصناف، حسابات، جهات تعامل):**
     - يتم قراءة نسخة السيرفر الحالية (`server_payload.version`).
     - يتم تحديث السجل المحلي في Dexie ببيانات `local_payload` وتحديث نسخته لتطابق السيرفر.
     - يتم حذف العملية القديمة المتعارضة من `outbox`، وإدراج عملية جديدة برقم `base_version = server_payload.version`، بحيث يقبلها السيرفر عند الدفع القادم.
     - وسم النزاع كـ `keep_local` وتسجيل توقيت الحل.

## 2. معمارية المصادقة والأمان أوفلاين (Offline Auth Architecture)

### 2.1 تخزين الجلسة ومكافحة التلاعب (Integrity & Expiry)
1. **لا تخزين لكلمات المرور نهائياً:** لا يتم تخزين كلمات المرور كنص صريح أو حتى كـ MD5 محلياً. تعتمد المصادقة أوفلاين على استمرار صلاحية الجلسة الموثقة مسبقاً (`validated_session`).
2. **حد أقصى لصلاحية الجلسة أوفلاين (`OFFLINE_SESSION_MAX_AGE_MS`):**
   - مدة الصلاحية القصوى: **7 أيام** من آخر اتصال ناجح بالسيرفر.
   - إذا حاول المستخدم فتح التطبيق أوفلاين بعد مرور أكثر من 7 أيام، تُعتبر الجلسة منتهية ويُطلب منه الاتصال بالإنترنت لإعادة المصادقة.
3. **بصمة النزاهة الرقمية (Session Signature):**
   - يتم احتساب توقيع أمان مشفر عبر Web Crypto API (`SHA-256`) يدمج: `userId + role.name + is_active + offlineExpiresAt + SALT`.
   - عند تحميل الجلسة أوفلاين، يتم التحقق من صحة البصمة لمنع أي تعديل يدوي في `localStorage` لصلاحيات الدور أو تاريخ الانتهاء.

### 2.2 فرض قيود الفروع والأدوار محلياً (Role & Branch Enforcement)
- يُحدد للمستخدم قائمة الفروع المخصصة له (`branches`) والفرع الافتراضي الحالي (`currentBranchId`).
- لا يمكن للمستخدم التبديل لفرع غير مخصص له إلا إذا كان يحمل دور مدير عام (`Admin`).
- كافة العمليات المنشأة محلياً ترتبط تلقائياً بـ `currentBranchId` ولا تقبل التزييف.

### 2.3 الرصد الفوري والتعطيل التلقائي عند العودة للاتصال (Instant Online Revocation)
- عند عودة اتصال الجهاز بالإنترنت (`window.addEventListener('online')`)، يقوم التطبيق تلقائياً بفحص خلفي صامت لملف المستخدم الشخصي في جدول `profiles` على السيرفر:
  ```typescript
  const { data: profile } = await supabase.from('profiles').select('is_active').eq('id', userId).single();
  if (!profile || profile.is_active === false) {
    // إنهاء الجلسة فوراً ومسح التخزين
    await logout();
    // إظهار رسالة تنبيه واضحة
  }
  ```
- في حال كان الحساب معطلاً (`is_active === false`) أو محذوفاً:
  1. يتم مسح رمز الجلسة والبيانات المخزنة محلياً فوراً.
  2. يتم توجيه المستخدم فوراً إلى شاشة الدخول `/login`.
  3. تظهر رسالة باللغة العربية: `"تم تعطيل حسابك من قبل إدارة النظام. تم تسجيل الخروج فوراً."`.

## 3. التكامل مع واجهة المستخدم (UI Integration)
1. **مسار النزاعات:** إضافة مسار `/sync-conflicts` في موجه التطبيق `src/app/routes.tsx`.
2. **شريط الحالة والمؤشر:**
   - شريط `SyncStatusPill` يعرض شارة حمراء نابضة بالنزاعات عند وجود أي نزاع غير محلول.
   - النقر على الشارة ينقل المستخدم مباشرة إلى `/sync-conflicts`.
3. **عنصر القائمة الجانبية:** إضافة رابط مباشر لشاشة "معالجة التعارضات" في الشريط الجانبي مع إظهار عدد النزاعات النشطة.
